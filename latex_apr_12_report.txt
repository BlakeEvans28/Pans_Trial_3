% LETTER OF TRANSMITTAL
\chapter*{Letter of Transmittal}
\addcontentsline{toc}{chapter}{Letter of Transmittal}

This report presents the current state and publication case for \textit{Pan's Trial}. It was prepared to help instructors, engineers, and potential publishing partners understand what the game is, why the game is commercially promising, how the software is built, and what evidence supports further development.

The work period covered by this report runs from the original March--May 2026 implementation into the May 2026 web and multiplayer hardening pass. The current build now includes the full gameplay loop: draft, coin flip, Omen reveal, Traversing the Labyrinth, Appeasing Pan, all four Pan requests, post-Appeasing card placement, victory resolution, match summary, and Play Again. It also includes a browser build, a hosted room-server path, LAN-ready room-code multiplayer, a How To Play screen, Settings, health-left HUD, themed board art, and an Appeasing Pan legend that explicitly marks strongest-to-weakest role order [3][4][5].

The result is a publishable prototype, not merely a class exercise. The rules are complete, the interface is playable, the browser package is deployable, and the current regression suite reports 100 passing rule, multiplayer, and UI tests. The strongest experimental result is fairness: in a 100-game headless balance run, Player 1 won 52 games and Player 2 won 48, while stronger AI profiles defeated weaker profiles at high rates [6]. The strongest business result is reach: the game can become a one-link browser experience, then expand into Steam, itch.io, and mobile/tablet releases with the same core rules engine.

We recommend continued implementation as a web-first game with desktop and mobile follow-up. The next engineering investments should be a public hosted URL, a first-run tutorial, a simple Solo Tutorial opponent, stronger reconnect/leave messaging, and production deployment with HTTPS. The next product investments should be a polished trailer, a public demo build, cosmetic board/theme packs, and a premium or pay-what-you-want launch test.

% ABSTRACT
\chapter*{Abstract / Executive Summary}
\addcontentsline{toc}{chapter}{Abstract/Executive Summary}

\textit{Pan's Trial} is a two-player tactical card-and-labyrinth game. Each match begins with a public draft, then assigns four card families to changing roles: Walls, Traps, Ballista, and Weapons. Players traverse a 6x6 toroidal labyrinth, collect or trigger cards, fight with weapon cards, and periodically enter Appeasing Pan, a second-phase contest where card strength determines who receives first choice of a powerful request. Those requests can restructure suit roles, steal life, ignore Pan's demands, or shift an entire row or column.

The game is relevant because it solves a real design problem: a clever tabletop prototype with many state-heavy rules becomes easier to learn, enforce, test, and publish when implemented digitally. The digital version tracks health, movement, wraparound edges, suit-role changes, combat legality, request resolution, and card placement automatically. The current interface also shows the phase banner, health remaining, Omen role legend, and Appeasing strength arrow so players do not need a separate rules document to understand the current state [3][5].

The final game is implemented in Python with Pygame-CE. The codebase separates the headless rules engine from the UI, multiplayer layer, and build scripts. That separation lets the same engine support desktop play, automated tests, balance simulations, and a browser-based WebAssembly build. The browser build is generated by \texttt{build\_web.py}; the room server in \texttt{room\_server.py} can serve both \texttt{WEB\_BUILD/site} and the room API from the same URL [3][4][5].

The business case is strong enough to justify further implementation. Games are a mainstream market: the ESA reports more than 205 million Americans play video games, and Newzoo estimated the 2025 global games market at \$188.8 billion with 3.6 billion players [8][9]. \textit{Pan's Trial} does not need mass-market scale to be viable. It can target strategy players, tabletop players, students, families, and small competitive communities through the low-friction web demo, then expand to paid desktop/mobile releases, cosmetic content, and educational licensing.

The experimental evidence supports continuing. The current test suite contains 100 passing tests, and the 100-game balance study produced a 52--48 seat split, average final damage values within 0.02 points, and a clear skill ladder where stronger agents beat weaker agents [6]. These results do not prove the game is finished, but they show the core loop is fair, testable, and worth publishing.

% INTRODUCTION
\chapter*{ Introduction}
\addcontentsline{toc}{chapter}{I Introduction}

\section*{Problem and Relevance}

Many tabletop strategy games are exciting because they ask players to manage a large state space: board position, hidden resources, role changes, damage, timing, and future threats. That same richness can also become a barrier. If players must constantly ask whether movement wraps, whether a wall blocks a Ballista path, or which suit is strongest in the current phase, the cognitive load shifts away from strategy and toward rule maintenance.

\textit{Pan's Trial} addresses that problem by digitizing a compact but layered two-player design. The game keeps the tabletop feel of cards, drafting, and spatial tactics, while the software handles legality, feedback, state transitions, and scoring. The result is easier to learn and easier to publish than the original physical prototype.

\section*{Why This Design Should Be Built Larger}

The design deserves further development for four reasons. First, it has a distinct mechanical identity: it is not only a card game and not only a board game. Second, it is replayable because the draft, Omen order, and board state change every match. Third, it has already been engineered with testable rules and deployable builds. Fourth, the web version gives the project a realistic path to audience growth because a judge, friend, or customer can try it from a URL instead of installing a Python environment.

The publication opportunity is especially important. A web-first launch supports sharing, classroom testing, tournament nights, and content-creator demonstrations. A premium desktop/mobile release can follow once the tutorial, polish, and stability are stronger. The current project is therefore best understood as a vertical slice for a larger commercial game.

% BACKGROUND
\chapter*{Summary and Background}
\addcontentsline{toc}{chapter}{Summary and/or Background}

A game is a rule-governed system with goals, constraints, conflict, and feedback. A game mechanic is one repeatable action or rule pattern that creates decisions. In \textit{Pan's Trial}, examples of mechanics include drafting a card, moving through the labyrinth, resolving a Ballista shot, playing an Appeasing card, and choosing a Pan request.

The goal is simple: avoid losing 25 health. The path to that goal is intentionally layered. A player must choose which high-rank cards to draft, which board routes to take, when to pick up a card, when to fight, and when to use Pan requests to change the future shape of the game.

\section*{Core Rule Vocabulary}

\begin{itemize}
\item \textbf{Labyrinth}: the 6x6 toroidal board. Leaving one edge wraps to the opposite edge.
\item \textbf{Omen}: one of the four Jack cards that assigns a suit family to a role.
\item \textbf{Roles}: Walls block movement, Traps reduce health, Ballista cards create line movement, and Weapons become combat cards.
\item \textbf{Traversing}: the main movement phase.
\item \textbf{Appeasing Pan}: the second phase where both players play a hand card to win request priority.
\item \textbf{Requests}: Restructure, Steal Life, Ignore Us, and Plane Shift.
\end{itemize}

The digital implementation also reframes card presentation through the theme. Tens are Satyrs, Queens are Oracles, Kings are Heroes, and suits are shown as color families. This helps the game feel like a mythic contest rather than a raw deck simulation [3][5].

\section*{Argument 1: The Game Has a Publishable Hook}

\textit{Pan's Trial} can be pitched in one sentence: draft cards, survive a shifting labyrinth, and bargain with Pan for power. That is a usable hook because it communicates genre, conflict, and theme. The game also creates moments that are easy to explain visually: a player lands on a trap, a Ballista line opens across the maze, the Omen roles swap, or the Appeasing winner points the board in a new direction.

\section*{Argument 2: The Digital Version Solves the Hard Parts}

The game's most error-prone tabletop rules are exactly the rules software is good at enforcing: toroidal movement, line-of-sight Ballista targeting, weapon legality, simultaneous Appeasing card play, rank-vs-role comparisons, and post-Appeasing hole placement. The interface also keeps the important state visible. In the current build, the right-side Omen legend shows role order, and during Appeasing Pan it adds a clear strongest-to-weakest arrow [5].

\section*{Argument 4: The Market Supports a Web-First Strategy}

The business argument does not require claiming that \textit{Pan's Trial} will become a blockbuster. It only requires showing that the game can reach a focused audience at low distribution cost. The ESA reports more than 205 million Americans play video games, with large portions of the audience playing online and with other people [8]. Newzoo estimated the 2025 global games market at \$188.8 billion and 3.6 billion players [9]. A small tactical game can succeed inside that large market if it is easy to try, easy to share, and visually clear.

Web-first deployment is the correct first commercial path because it reduces friction. A player can open one URL, create a room, share a code, and play. Once a web demo proves retention, the same rules engine can support premium desktop, Steam, itch.io, and mobile versions. Steam's official Direct fee is \$100 and becomes recoupable after \$1,000 adjusted gross revenue [10]. Itch.io supports configurable creator revenue sharing, including pay-what-you-want pricing [11]. These platforms make small-scope commercial testing realistic.

\section*{Rules of Play}

\begin{enumerate}
\item \textbf{Setup and draft.} Each match begins with a shuffled 6x6 labyrinth made from the Ace-through-9 cards. The four Jacks are set aside as Omens, and the draft pool is the 12 face cards made from the four Satyrs (10), four Oracles (Queen), and four Heroes (King). A coin flip decides who drafts first. Players alternate ten picks total. All Satyrs and Oracles are drafted, but only two Heroes may be taken; the two Heroes left in the pool become the player identity cards.

\item \textbf{Omen assignment.} After the draft, the four Omens are revealed in order. That order assigns one suit to each board role: Walls, Traps, Ballista, and Weapons. A card keeps its suit for the entire match, but its effect depends on the current Omen mapping. Because of that design, the same suit can block movement in one match, become combat material in another, and later change again if a Pan request restructures the roles.

\item \textbf{Traversing the Labyrinth.} Traversing is the main board state and begins with Player 2 in the current implementation. One Traversing cycle contains six total turns, three per player, with the active player alternating after each move, pickup, or forced pass. On a turn, a player may move one space up, down, left, or right, or spend that turn interacting with the card on the tile they already occupy. The board is toroidal, so leaving one edge wraps to the opposite edge. A move into a Wall is illegal. Landing on or picking up a Trap adds that card to the player's lost-health pile and leaves an empty hole. Landing on or picking up a Weapon adds that card to the player's hand. Landing on a Ballista opens a targeting state where the player chooses any reachable tile in a straight line until a Wall blocks the path. The resulting Ballista launch moves the player without triggering the destination tile's effect. The primary gameplay interface during Traversing is shown in Figure~\ref{fig:board}, including the toroidal board, health display, and Omen legend.

\item \textbf{Combat.} Combat is a temporary substate inside Traversing. It begins whenever both players occupy the same tile, whether that happens through normal movement or a Ballista launch. Each player who has at least one card whose current suit role is Weapons may play one such card from the normal hand. The moving player chooses first, then the opponent. Each played weapon card is added to the opposing player's lost-health pile, so both players can deal damage in the same collision if both have usable weapons. A player loses immediately when the total value of cards in that lost-health pile reaches 25 or more.

\item \textbf{Appeasing Pan.} After six Traversing turns, the game checks whether both players still have at least one hand card. If both do, the match enters Appeasing Pan; if either player has no hand cards left, Appeasing Pan is skipped and the game returns directly to another Traversing cycle. During Appeasing Pan, both players submit one hand card. Winner determination uses the phase hierarchy Walls $>$ Traps $>$ Ballista $>$ Weapons. Rank matters only when both played cards share the same suit. The winner gains first request priority. The Appeasing Pan resolution interface is shown in Figure~\ref{fig:appeasing}, and the request chooser is shown in Figure~\ref{fig:requestchoice}.

\item \textbf{Pan requests.} The Appeasing winner chooses one request first, and the loser chooses a different request second unless the winner uses Ignore Us, which ends the request sequence immediately. Restructure selects two suits and swaps their assigned roles for all matching cards on the board and in players' hands; the interface is shown in Figure~\ref{fig:restructure}. Steal Life exchanges one lost-health card from the chooser with one from the opponent; the resolution screen is shown in Figure~\ref{fig:steallife}. Ignore Us ends the request state with no second request. Plane Shift chooses a row or column and wraps it by one tile, moving cards and any player standing on that line with it; the interaction screen is shown in Figure~\ref{fig:planeshift}.

\item \textbf{Hole placement and reset.} After requests resolve, the Appeasing loser places the two played Appeasing cards into open holes when possible. A legal hole is an empty board space that is not currently occupied by a player. If fewer than two valid holes remain, any unplaced cards return to that loser's hand. If a request leaves a player with no legal movement because Walls now trap them, that player is forced to pass the next three Traversing turns. After hole placement or card return, the game resets to Traversing and the next movement cycle begins.
\end{enumerate}

\section*{How Another Engineer Can Add a Feature}

A new feature should follow the existing boundaries:

\begin{enumerate}
\item Add or update an action in \texttt{engine/actions.py} if the feature changes game state.
\item Implement rule behavior in \texttt{engine/game\_state.py}.
\item Add UI rendering and input handling in \texttt{ui/game\_screen.py} or the relevant screen.
\item Add tests in \texttt{tests/test\_rules.py}.
\item If the feature affects Two Player, verify the action and state are serializable through \texttt{multiplayer/serialization.py}.
\item Run the tests and rebuild the browser package.
\end{enumerate}

This process is already proven by the recent Appeasing legend update: one UI helper was added, tests verified phase-specific behavior, and the web package was rebuilt so the browser bundle contained the change [4][5].

The remaining publication gaps are onboarding and production hosting, not missing core mechanics.

% DISCUSSION
\chapter*{Discussion of Results}
\addcontentsline{toc}{chapter}{Discussion of results}

\section*{Implications for the Game Design}

The balance results imply that the core system is healthy. The game produces close seat fairness while still rewarding stronger play.  It means the game can be marketed as tactical rather than random, while still preserving enough uncertainty through draft order, Omen assignment, board topology, and Pan requests.

The main design risk is pacing. An average of 235.83 logged actions per game may be longer than ideal for a casual web audience. Plane Shift also appears more often than the other requests, which may mean it is the most generally useful request. Future tuning should focus on match length, clearer early-game goals, and request balance rather than rebuilding the core rules.

\section*{Implications for Website and App Deployment}

The web version should become the lead platform. A browser game has three advantages: instant access, easy sharing, and no install barrier. This matters for judges, classrooms, friends, and early customers. A player should be able to open one URL, choose Two Player, create a code, and start a match.

A mobile/tablet app is also natural because the game is turn-based, board-centered, and mouse/touch friendly. The board is already a 6x6 grid, most actions are clicks, and the game does not require twitch reflexes. A tablet version could become the best long-term play format because it resembles a digital board game table.

The desktop executable still matters, but mainly as a premium downloadable build and offline fallback. It is less important for early audience growth than the website because every install step reduces the number of people who will try the game.

\section*{Monetization Strategy}

\textit{Pan's Trial} can make money because its replay value comes from systems rather than expensive content volume. The team does not need hundreds of levels, voice acting, or live-service infrastructure to ship a satisfying first product. The draft, randomized Omens, tactical board, and room-code multiplayer create repeated variation from a small rules set.

The safest monetization principle is to avoid selling power. Paid content should be cosmetic, convenience-based, or access-based. The fairness evidence is one of the project's strongest assets, so monetization should not damage competitive trust.

\section*{Implications Beyond the Project}

This project also demonstrates a broader software-engineering point. Digital game implementations are not only entertainment artifacts; they are experimental systems. Because \textit{Pan's Trial} has a headless engine, the team can simulate balance, test edge cases, and make evidence-based tuning decisions. That turns design iteration from opinion into measurable engineering.

% CONCLUSIONS
\chapter*{Conclusions}
\addcontentsline{toc}{chapter}{Conclusions}

This report describes the final current state of \textit{Pan's Trial}, explains how the game is built, presents experimental evidence, and argues for continued publication-focused development. The game is now a complete two-player tactical card-and-labyrinth experience with draft, Omens, Traversing, Appeasing Pan, requests, card placement, game over, Play Again, browser packaging, and room-code multiplayer.

The evidence supports moving forward. The current test suite reports 100 passing tests. The balance simulation shows near-even seats and strong skill differentiation. The market context shows that games are a large, socially connected entertainment category, and the project's web build gives it a practical route to player access [8][9].

The next work should not be a redesign. It should be productization:

\begin{itemize}

\item add an in-game first-run tutorial and a Solo Tutorial mode;
\item harden reconnect, leave, and server-error messaging;
\item tune match length and request balance using the existing simulation harness;
\item prepare a public trailer, screenshots, and store-page copy;
\item test monetization through a web demo, itch.io release, Steam release, and later mobile/tablet build.
\end{itemize}

With those steps, \textit{Pan's Trial} can move from course project to commercial indie strategy game. Its strongest selling point is not only that it works. It is that the game is already structured like something engineers can keep improving and players can realistically access.

\chapter{Engineering Handoff Checklist}

\begin{itemize}
\item Run \texttt{tests/test\_rules.py} before and after rule changes.
\item Keep rules in \texttt{engine/}; avoid placing core legality decisions only in UI code.
\item Add UI affordances for every multi-step choice.
\item Verify web build behavior after UI changes because the browser canvas and desktop window can differ.
\item Rebuild \texttt{WEB\_BUILD/site} after source changes intended for browser play.
\item When testing multiplayer, use the room server so the static site and room API share one origin.
\item For public hosting, use HTTPS for both the page and the room API.
\end{itemize}
